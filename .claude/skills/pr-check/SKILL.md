---
name: pr-check
description: PR 전 충돌 검사 — main과의 git 충돌, 같은 화면 경로·마이그레이션 번호 중복, 다른 열린 PR·최근 머지와의 파일·기능 겹침을 찾고 해결 방법을 제안한다. PR을 올리기 전, push 전, "충돌 있나?" 확인할 때 사용. /handoff가 PR 전에 반드시 실행한다.
---
1. 미커밋 변경이 있으면 알리고 커밋할지 묻는다 (git 충돌 검사는 커밋된 내용 기준).
2. `scripts/check-conflicts.sh` 실행. 결과를 세 구역으로 요약한다.

3. **❌ git 충돌** (main과 합치면 충돌하는 파일)
   - `/sync`(rebase)로 해결한다. 파일별로 양쪽 변경 의도를 `git log -p origin/main -- <file>`로 확인해 설명하고 해결안을 제시한다.
   - 충돌 파일이 **다른 사람의 기능 파일이거나 공용 파일**이면 임의로 해결하지 않는다. 선택지를 주고 사용자에게 묻는다 (예: 내 쪽 경로·이름 분리 / 상대 변경 위에 내 변경 얹기 / 담당자와 상의).

4. **❌ 같은 경로·번호**
   - 화면 경로(`frontend/src/app/<route>/page.tsx`)가 main에 이미 있거나 다른 PR도 만든다 → 같은 화면을 두 사람이 만들고 있다는 뜻. 경로 분리(`/<다른이름>`) 또는 한쪽으로 합치기를 사용자에게 묻는다. 경로를 바꾸면 메뉴(`app-sidebar.tsx`)·링크·계약 문서의 사용처도 함께 고친다.
   - 마이그레이션 번호 중복 → 내 파일 번호를 main의 마지막 번호 +1로 바꾼다 (`git mv`). 다른 열린 PR과 겹치면 늦게 머지하는 쪽이 올린다고 안내.

5. **⚠️ 겹침 경고** (지금은 git 충돌이 아니지만 머지 순서에 따라 충돌·동작 깨짐 가능)
   - 다른 열린 PR과 같은 파일·기능: 작성자를 알려주고, 먼저 머지할 쪽을 정하자고 제안. 공용 파일(`app-sidebar.tsx`, `layout.tsx`, `api-client.ts`, `config.py` 등)이면 변경을 최소화하고 PR 본문에 "PR #N과 같은 파일 수정"을 적고 그 작성자를 리뷰어로 지정.
   - 내 브랜치 이후 main에서 바뀐 파일: `/sync` 후 검증 명령(CLAUDE.md "명령")을 다시 돌려 동작을 확인.

6. 해결했으면 `scripts/check-conflicts.sh`를 다시 실행해 ❌가 없어질 때까지 반복. 결과(❌ 0개, 남은 ⚠️ 목록)를 PR 본문 "확인"에 한 줄로 적는다.
