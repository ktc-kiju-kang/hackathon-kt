해커톤 파이프라인 지도

주제 공개부터 제출까지를 그림으로 봅니다. 입구는 make 하나이고, 사람이 멈춰 결정하는 곳은 세 게이트(G1·G2·G3)와 머지뿐입니다. 나머지는 에이전트와 스크립트가 돌리고, 결과는 PR 본문과 문서 8개에 근거로 남습니다.

3번사람이 결정하는 게이트 (정의서 · 분배표 · 테이블 초안)
2~4.5분ship 한 번 (CI 가벼우면 2분, 키트 e2e 포함 4~4.5분)
32분리허설: REQ 1개 → Issue 3개 → 루프로 전부 머지
8개제출 문서. 상태·숫자·AI 기록은 make record가 채움

누가 무엇을 하나

세 줄로 나눈 흐름입니다. 위 줄은 사람, 가운데는 에이전트, 아래는 make 스크립트. 화살표를 따라가면 하루가 보입니다.

사람이 결정에이전트make 스크립트

ship 한 번은 어디에 시간을 쓰나

작업 브랜치가 main에 들어가는 유일한 길입니다. 총 시간은 10/10 실주행에서 잰 값(4분 26초)이고 단계별 길이는 어림값입니다. 붉은 단계에서는 멈추고 PR을 그대로 둡니다.

①main 반영 → push → 초안 PR (CI가 나란히 시작)
②verify: lint·타입·pytest·vitest·빌드·문서
③충돌 검사: 열린 PR과 같은 파일·기능이면 경고
④e2e: 격리 배포에 시험, 기록은 되돌림
⑤PR 본문 "확인" 절 · 초안 해제 · 마이그레이션 대조
⑥AI 리뷰 60점 블록. 재리뷰는 이전 지적 처리부터
⑦Issue 근거 댓글. 머지 조건·G3·초안과 다른 마이그레이션이면 멈춤
⑧CI 대기(잠금 밖) → 잠금 → squash 머지 → 라벨 정리
⑨main 확인. 같은 트리면 verify 생략

명령언제하는 일

make ship작업 끝9단계. 루프는 SHIP_NO_MERGE=1 기본, 머지까지 맡기면 TICKET_LOOP_MERGE=1
make serve · stop · status로컬 배포 확인프로덕션 빌드 + 스모크 (버전 = HEAD)
make e2e확인용단위 + 격리 배포 E2E. 기록 커밋은 record만
make record2~3시간마다, 제출 전시험 기록 · AI 활용 기록 · README 숫자를 자동 PR로 머지
make audit정책 확인 뒤, 제출 전gitleaks · npm audit(운영) · pip-audit → compliance 4절
make claims · release ISSUE=n · lock-status누가 뭘 잡았나선점 목록 · 선점 해제 · 머지 잠금
make submit-check제출 직전4가지 확인 → 포털에 넣을 40자 SHA
ship이 멈추는 흔한 이유
메시지뜻할 일
머지 조건이 풀리지 않아FE가 같은 REQ의 BE보다 먼저 끝남PR 그대로 두고 BE 머지 뒤 ship 다시 (루프는 다음 틱에 스스로)
테이블 SQL 초안이 있는 계약이 바뀜G3사람이 스키마 보고 GitHub에서 머지
마이그레이션이 계약 초안과 다름초안과 다른 컬럼·제약초안에 맞추거나 계약 PR 먼저. 의도한 차이면 사람 머지
AI 리뷰 수정 필요차단·높음 또는 42점 미만지적을 고치고 커밋 → ship. 재리뷰는 이전 지적 처리 표로 수렴
CI 체크가 생기지 않음Actions가 꺼져 있음SHIP_NO_CI=1 make ship
머지 대기 중다른 사람이 머지 중기다린다. 15분 넘은 잠금은 자동 회수. make lock-status
