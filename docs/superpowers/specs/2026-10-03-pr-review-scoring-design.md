# PR 리뷰 자동 점검·점수 설계

- 날짜: 2026-10-03
- 상태: 설계 승인됨. 2026-10-04 갱신: `ty`는 PR #63으로 이미 도입·CI 차단(진단 0건)이라 절대 기준으로 채점한다
- 관련: `docs/SDLC.md`, `.claude/agents/reviewer.md`, `.claude/skills/handoff/SKILL.md`, 협업 규칙 2(승인 불필요)

> **구현 상태 확인 (2026-10-06)**: 설계 승인과 구현 완료는 별개다. 현재 `pr-review.yml`·채점 스크립트·테스트·`docs/review.md`·`docs/workflow.md`는 없고, reviewer도 점수 없는 지적 목록을 출력한다. 아래 흐름·점수표는 **미구현 설계**이며 기존 40/60 배점·85/70 판정선은 변경하지 않는다.
> 현재 운영 절차·근거는 [SDLC](../../SDLC.md), 실행 전 검토 항목은 [구현 계획](../plans/2026-10-04-pr-review-scoring-ci.md#구현-착수-전-재확인)에 둔다. 이 점수는 공식 해커톤 점수나 SDLC 성숙도 점수가 아니다.

## 1. 목적
PR을 올리는 시점에 **점수와 코드 분석**이 PR에 남고, 누구나 한눈에 볼 수 있게 한다.
SDLC 흐름에서 리뷰 단계를 "reviewer 에이전트를 돌린다"는 관례에서, **형식·점수·최신성이 검증되는 절차**로 정의한다.
린트·타입 검사(ESLint, ruff, ty) 결과도 점수에 반영한다.

배경(2026-10-03 설계 당시 기록): 머지된 PR 38건 중 22건(**57.9%**)이 AI 리뷰 결과를 본문에 남겼지만 형식이 제각각이고 점수가 없으며, 템플릿 체크박스를 실제로 체크한 PR은 12건이었다. 당시 대상 PR 목록·집계 명령은 이 문서에 보존되지 않아 이번에 재현한 측정값은 아니다. 개선 효과를 비교하려면 대상 기간·PR 목록·판정 기준부터 고정한다.

## 2. 범위
**포함**: 점수표, 리포트 형식, CI 자동 채점·집계·코멘트, 린트·타입 검사 반영, `reviewer`·`/handoff`·PR 템플릿 갱신, 문서(`docs/review.md`).
**제외 (논의 끝에 뺌)**: CI에서 AI 리뷰 실행(API 키·관리자 권한 필요), 사람 교차 리뷰 의무화, CODEOWNERS, 필수 체크 지정, 정기 헬스체크, 관리자 설정.

## 3. 흐름
```
/handoff → reviewer(AI) 리뷰 → 표준 리포트 → PR 본문 "AI 리뷰" 블록 → PR 생성
PR 이벤트(opened·synchronize·edited·reopened) → CI "PR Review" → 코멘트 1개 갱신
```
- AI 리뷰는 **로컬**(`/handoff`)에서 한다. CI는 **객관 점검(린트·타입 포함), AI 블록 파싱·검증, 집계, 가시화**를 한다.
- 설계 목표는 **보고 전용·비차단**이다. 점수는 PR 코멘트와 잡 요약(`$GITHUB_STEP_SUMMARY`)으로 보여 준다. **필수 체크가 아니라는 것과 잡이 항상 성공한다는 것은 다르다**. 설치·API·파싱 실패까지 보고가 남는지는 구현 시 검증해야 한다.

## 4. 점수표 (100점)

### 4.1 자동 점검 — CI가 채점 (40점)
| 항목 | 배점 | 기준 |
|---|---|---|
| **린트·타입 검사** | **10** | 아래 4.1.1 |
| 이슈 연결 | 6 | 제목 type이 `docs`·`chore`·`ci`면 만점(면제). 그 외: `Closes/Fixes/Resolves #n` = 6, `#n` 참조만 = 4, 없음 = 0 |
| 테스트 동반 | 8 | 코드 변경 없음(문서·설정만) = 8. 코드 변경 + 테스트 파일 변경 = 8. 코드 변경 + 테스트 없음: 변경된 코드 줄 ≤ 30이면 5, 그 이상이면 0 |
| 문서·계약 동반 | 5 | 계약 영향 파일(`backend/app/routers/**`, `backend/app/schemas/**`, `frontend/src/features/*/api.ts`)이 바뀌었는데 `docs/contracts/**`가 안 바뀌면 0. 해당 없거나 함께 바뀌면 5 |
| PR 크기 | 4 | 제외 파일 뺀 추가+삭제 ≤ 400 = 4, ≤ 800 = 2, 초과 = 0 |
| 커밋 규약 | 3 | 머지 커밋을 뺀 커밋 중 `^(feat\|fix\|refactor\|docs\|chore\|test\|perf\|ci)(\([^)]+\))?: ` 형식의 비율 × 3 (반올림) |
| PR 본문 충실도 | 4 | 본문 200자 이상 = 1, `## 변경`(또는 `## 변경 내용`) 섹션 = 1, `## 검증`(또는 `## 확인`) 섹션에 항목 1개 이상 = 2 |

#### 4.1.1 린트·타입 검사 (10점)
| 도구 | 배점 | 대상 | 기준 |
|---|---|---|---|
| ESLint | 3 | `frontend/**` 변경이 있을 때 | 오류 0건 = 3, 오류 있음 = 0 (경고는 감점 없이 표시) |
| ruff check | 3 | `backend/**` 변경이 있을 때 | 위반 0건 = 3, 있음 = 0 |
| ruff format | 2 | `backend/**` 변경이 있을 때 | 포맷 차이 없음 = 2, 있음 = 0 |
| ty | 2 | `backend/**` 변경이 있을 때 | 진단 0건 = 2, 1~2건 = 1, 3건 이상 = 0 |
- 해당 영역 변경이 없으면 그 도구는 **실행하지 않고 만점**(해당 없음으로 표시).
- **ESLint·ruff·ty 모두 현재 저장소가 깨끗**(2026-10-04, PR #63로 `ty` 33건 해소, CI 필수 체크)해서 **절대 기준**(건수)으로 채점한다. base 커밋 비교는 필요 없다.
- `ty`는 베타(0.0.x)라 버전을 고정(`requirements-dev.txt`)해 진단이 바뀌지 않게 한다.
- 이 점수는 **CI(`frontend`·`backend`)의 린트 단계와 별개로** 다시 계산한다. CI는 합격·불합격만 알려 주고, 이 점수는 **도구별 건수와 위치**를 PR 코멘트에 보여 준다.

#### 4.1.2 판정 기준 세부
- **코드 파일**: `backend/app/**/*.py`, `frontend/src/**/*.{ts,tsx}`. 단 `frontend/src/components/ui/**`(shadcn 생성 코드)와 테스트 파일은 제외.
- **테스트 파일**: `backend/tests/**`, `*.test.ts`, `*.test.tsx`.
- **크기 제외**: `package-lock.json`, `frontend/src/components/ui/**`, `backend/data/**`.
- CI 합격 여부(`frontend`·`backend` 등)는 점수에 넣지 않는다. 이미 별도 체크로 표시된다.

### 4.2 AI 리뷰 — `reviewer`가 채점 (60점)
| 항목 | 배점 | 보는 것 |
|---|---|---|
| 정확성 | 15 | 버그, 잘못된 로직, 처리 안 된 예외·Promise, 경계 조건 |
| 보안·비밀값 | 10 | 키·토큰 노출, 입력 검증, 권한 체크, 프롬프트 인젝션 |
| 계약·스키마 일치 | 10 | 계약 문서 ↔ 스키마 ↔ 프론트 타입, mock이 계약과 같은지 |
| 설계·구조 | 10 | 영역 경계, import 방향, 중복, 단순성 |
| 테스트 품질 | 10 | 의미 있는 테스트인지, 실패해야 할 때 실패하는지, 놓친 경로 |
| 배포·운영 안전 | 5 | 마이그레이션 호환, 환경변수, 롤백 가능성, 배포 영향 |

- 감점 앵커는 `docs/review.md`에 둔다 (심각 = 해당 항목 배점의 50% 이상 감점, 보통 = 20~40%, 경미 = 10% 이내). 모든 감점은 **`파일:줄` 근거**를 인용해야 한다.
- 항목에 해당 사항이 없으면(예: DB 변경 없음) "해당 없음"으로 적고 만점 처리한다.
- `reviewer`는 린트·타입 결과를 **참고 입력**으로 쓴다(예: `ty`가 가리킨 타입 결함이 실제 버그인지 판단). 린트 점수 자체는 CI가 채점하므로 AI 항목에서 중복 감점하지 않는다.

### 4.3 판정
| 총점 | 판정 |
|---|---|
| 85 이상 | **머지 가능** |
| 70~84 | **지적 처리 후 머지** |
| 70 미만 | **수정 필요** |
- 여기서 "머지 가능"은 **리뷰 참고 판정**이다. 필수 CI·차단 지적·요청한 담당자 리뷰·사람의 머지 결정을 대체하지 않는다.
- **차단 이슈가 1건이라도 있으면 점수와 무관하게 "수정 필요"** 다. (차단 = 데이터 손실·비밀값 노출·배포 장애·보안 취약점·계약 파괴)
- AI 리뷰 블록이 없거나 형식이 틀리면 AI 점수는 0이고 판정은 **"AI 리뷰 필요"** 다 (자동 점수만 표시).

## 5. AI 리뷰 블록 형식
PR 본문 하단에 아래 블록을 넣는다. 마커 사이만 CI가 읽는다.

```
<!-- ai-review:start -->
## AI 리뷰
- 리뷰한 커밋: `abc1234`
- 총점: 52/60
- 판정: 지적 처리 후 머지
- 차단 이슈: 없음            (또는 `2건`)

| 항목 | 점수 |
|---|---|
| 정확성 | 13/15 |
| 보안·비밀값 | 10/10 |
| 계약·스키마 일치 | 10/10 |
| 설계·구조 | 8/10 |
| 테스트 품질 | 7/10 |
| 배포·운영 안전 | 4/5 |

### 변경 요약
### 구조·설계 평가
### 위험 분석
### 테스트 평가
### 지적 사항
| 심각도 | 위치 | 문제 | 제안 |
### 확인하지 못한 것
<!-- ai-review:end -->
```
- **파싱 규칙**: `리뷰한 커밋: ` 뒤 7~40자리 16진수, `총점: N/60`, `차단 이슈: 없음|N건`, 항목 표의 6개 점수.
- **검증**: (a) 항목 점수 합 = 총점, (b) 각 항목 ≤ 배점, (c) 6개 항목이 모두 존재. 하나라도 틀리면 형식 오류(AI 0점)와 이유를 코멘트에 적는다.
- **섹션 6개**(변경 요약·구조·설계 평가·위험 분석·테스트 평가·지적 사항·확인하지 못한 것)는 CI가 존재만 확인하고 내용은 판단하지 않는다. 누락은 경고로만 표시한다.

## 6. CI 설계
- **파일**: `.github/workflows/pr-review.yml`, `scripts/pr_review_score.py`(표준 라이브러리만, `gh` CLI 사용), `scripts/test_pr_review_score.py`.
- **트리거**: `pull_request` — `opened`, `synchronize`, `edited`, `reopened`. `pull_request_target`은 쓰지 않는다. PR당 `concurrency`로 이전 실행을 취소한다.
- **권한**: `contents: read`, `pull-requests: write`, `issues: write`(PR 코멘트는 issues API).
- **절차**:
  1. 스크립트 자체 테스트(`python -m unittest`)
  2. PR 메타·파일 목록·커밋 목록 조회
  3. **변경 영역 판단**(frontend/backend) → 해당 영역만 린트 실행
     - frontend: Node 20 설정, `npm ci`, `npx eslint --format json`
     - backend: Python 설정, `uv venv && uv pip install -r requirements-dev.txt`(CI와 같은 방식), `ruff check --output-format json`, `ruff format --check`, `ty check --output-format concise app tests evals`
  4. 자동 점검 채점
  5. 본문에서 AI 블록 파싱·검증
  6. **최신성 검사**: `리뷰한 커밋`이 PR 커밋 목록에 있는지, PR 최신 커밋과 같은지
  7. 코멘트 생성/갱신(마커 `<!-- pr-review-score -->`, 항상 1개), 잡 요약 출력
- **최신성**: 리뷰한 커밋이 최신이 아니면 "리뷰 이후 N개 커밋이 추가됨"을 경고로 표시하고 점수에 `(최신 아님)`을 붙인다. 점수 자체를 깎지는 않는다. 리뷰한 커밋이 PR에 없으면 형식 오류로 본다.
- **비차단**: 스크립트는 항상 종료 코드 0으로 끝난다(채점 불가·도구 설치 실패 시에도 코멘트로 알림하고 해당 항목은 "측정 못 함"으로 표시, 점수는 만점도 0점도 아닌 **제외하고 비율로 환산**).
- **토큰이 읽기 전용인 경우**(Dependabot, 포크 PR): 코멘트 단계의 403은 잡아서 건너뛰고 잡 요약만 남긴다.
- **보안**: PR 본문·제목·파일명·린트 메시지는 신뢰할 수 없는 입력이다. 정규식·JSON 파싱으로 **읽기만** 하고, 셸·`eval`·템플릿에 끼워 넣지 않는다. 코멘트에 인용할 때는 길이를 자르고 마크다운·멘션(`@`)·링크를 무력화한다.
- **PR 실행 경계**: `pull_request_target`은 쓰지 않는다. 포크·Dependabot의 읽기 전용 토큰 경로와 같은 저장소 PR의 쓰기 권한 경로를 구분해 검증한다. 의존성 설치·ESLint 설정/플러그인·PR에서 바뀐 채점 스크립트는 코드를 실행할 수 있다. **"정적 분석이므로 PR 코드를 실행하지 않는다"는 가정은 사용하지 않는다.** 쓰기 토큰을 가진 보고 단계와 신뢰하지 않는 코드 실행의 격리를 구현 전에 확정해야 한다.

## 8.1 구현 단위 (PR 분할)
공용 파일을 건드리고 크므로 **두 개로 나눈다.** 앞 단계가 머지된 뒤에 다음 단계를 한다. (`ty` 도입은 PR #63으로 끝남)
1. **자동 점검 CI** — `scripts/pr_review_score.py` + 테스트 + `pr-review.yml`. 이 PR 자체에서 워크플로가 실행돼 실환경 검증이 된다. AI 블록이 아직 없으므로 "AI 리뷰 필요"로 표시되는 것이 정상이다.
2. **리뷰 흐름 정의·채택** — `docs/review.md`, `docs/workflow.md`, `docs/SDLC.md` 허브, `reviewer`·`/handoff`·PR 템플릿 갱신, `CLAUDE.md`. 이 PR부터 AI 리뷰 블록을 실제로 붙여 end-to-end(점수 코멘트)를 확인한다.

## 9. 테스트 계획

## 10. 알려진 한계 (문서에도 명시)
- **AI 리뷰 블록은 작성자의 자기 보고다.** CI는 형식·합계·최신성은 검증하지만 **AI가 실제로 돌았는지는 검증할 수 없다.** 완전한 자동화는 CI에서 AI 리뷰를 돌려야 하며(API 키·관리자 권한 필요), 이번 범위에서 제외했다.
- 같은 모델이 만들고 같은 모델이 검토하므로 **독립성이 약하다.** 완화: `파일:줄` 근거 필수, 합계 검증, "확인하지 못한 것" 의무 기재, 점수는 참고용이며 머지 결정과 책임은 사람에게 있다.
- **`ty`는 베타(0.0.x)** 라 거짓 양성이 있을 수 있다. 버전을 고정하고 Dependabot 업데이트 PR에서 진단 변화를 확인한다.
- **린트·타입 점수는 변경된 영역을 대상으로** 실행한다. frontend 변경이 있으면 frontend 전체, backend 변경이 있으면 `app tests evals` 등 설정된 검사 범위를 보므로 같은 영역의 미변경 파일 문제도 포함될 수 있다. 반대로 실행하지 않은 영역의 상태는 증명하지 못한다.
- **해당 없음 만점·미측정 비율 환산은 품질 향상 증거가 아니다.** 문서 PR과 기능 PR, 미측정 항목이 다른 PR의 총점을 그대로 비교하지 않는다. 테스트 파일 동반·문서 변경·본문 길이는 대리 지표이며 실제 테스트 품질·계약 일치는 리뷰 증거로 판단한다.
- **오래된 리뷰는 새 변경의 검증이 아니다.** 현재 설계는 경고만 하고 감점하지 않으므로, 최신 SHA의 CI·추가 변경 리뷰 여부를 별도로 확인한다.
- 점수와 임계값(85/70)은 초안이다. 운영하며 조정하고, 조정하면 `docs/review.md`와 스크립트 상수를 함께 바꾼다.
- 자동 점검의 "코드 파일" 분류는 경로 규칙에 의존한다. 디렉터리 구조가 바뀌면(ADR 0007의 `features/` 이동) 규칙을 갱신해야 한다.
