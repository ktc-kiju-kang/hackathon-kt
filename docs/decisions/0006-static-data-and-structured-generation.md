# 0006. 공개 정적 데이터는 레포에, LLM 단발 생성은 구조화 출력 헬퍼로

- 상태: 채택
- 날짜: 2026-10-02
- 결정자: ktc-kiju-kang (#22, #23, #24 구현 중)

## 배경
- OpenAI Signals(CSV 9개, 약 2.4MB)와 그룹사 정보(5개)는 공개된 읽기 전용 데이터다. 처음 계약(#21)에는 Supabase 표와 마이그레이션으로 적었다.
- Radar·Product는 대화가 아니라 "입력 → 정해진 형태의 결과"를 만든다. 그런데 `LLMProvider`에는 structured output API가 없다.
- LLM이 근거 수치를 지어낼 위험이 있다. 이 기능의 핵심이 "데이터 근거"라서 치명적이다.

## 결정
1. **공개 읽기 전용 데이터는 `backend/data/`에 커밋**하고 처음 호출 때 메모리에 읽는다. 출처·라이선스는 README에 적는다. 사용자가 만드는 데이터만 DB에 둔다.
2. **단발 생성은 `app/agent/structured.py`** 로 한다.
   - `call_structured`: 결과 제출 도구 하나만 넘겨 호출하게 하고, 그 입력을 pydantic으로 검증한다. 스키마의 `$ref`는 펼치고, 형식 오류면 이유를 덧붙여 1회 재요청한다.
   - `CallBudget`: 요청당 LLM 호출 상한. 일시 오류와 형식 오류 재시도를 모두 센다.
   - `sse_stream`: 단계 이벤트 SSE, 15초 ping, 끊기면 취소.
3. **근거 수치는 서버가 채운다** (`trends.resolve_evidence`). LLM은 후보 id만 고르고, 클라이언트가 보낸 근거는 다시 채운다.

## 대안
- Supabase 적재: 데이터를 갱신할 때마다 수 MB짜리 마이그레이션이 필요하고, 테스트에서 DB를 monkeypatch해야 한다. 공유 DB에 직접 적재하는 건 금지다.
- 채팅 루프(`run_agent`) 재사용: 대화 기록이 필요 없는데 저장 형식과 append-only 규칙을 따라야 한다. 결과 형태를 강제하기도 어렵다.
- 공급자별 structured output: 어댑터마다 구현해야 한다. mock도 지원해야 한다.

## 결과 / 트레이드오프
- CI와 테스트가 실제 데이터로 돌고, DB 장애와 무관하게 트렌드 화면이 동작한다. 대신 데이터를 바꾸면 PR과 배포가 필요하다.
- 제출 도구 방식은 모델이 도구를 안 부르거나 출력이 길어 잘릴 수 있다 → 재요청과 `bad_output`으로 처리한다. 구현 중 실제 Gemini에서 `_strip_titles`가 `title` 필드를 지우는 어댑터 버그가 드러나 함께 고쳤다.
- 근거를 서버가 채우므로 LLM은 데이터에 있는 지표만 인용할 수 있다. 데이터에 없는 세부 기회는 `rationale`(AI 추론)로 구분해 보여준다.
