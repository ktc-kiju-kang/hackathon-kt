# SDLC 개선 실행 가이드 — 70점 기준선에서 100점 목표까지

> **문서 작성일: 2026-10-08. 실행 완료 보고서가 아니라 후속 작업 지침이다.**
> 기준선은 2026-10-06 비공식 평가(옛 `docs/SDLC.md` 8절, main 정리로 삭제됨 — git 이력 `ba5b896` 시점에서 확인)의 **70/100점**이다. 이번 문서 작성으로 점수를 올리지 않는다.
> 로컬 확인 기준: `ci/pr-review-score`, `dfd18f5`. 원격 main·배포·관리자 설정을 이번에 재평가한 것은 아니다.
> 개발 단계별 추천 모델·실제 스킬과 출처는 [파이프라인 가이드](PIPELINE-MODEL-SKILLS.md)를 참고한다.

## 1. 사용 방법과 인정 원칙

1. 아래 항목을 기능 또는 독립적으로 검증 가능한 변경 단위의 이슈로 묶고 **담당자·선행 항목·기한**을 정한다. 표의 역할은 배정 제안이며 특정 팀원에게 할당한 것이 아니다.
2. 작업 전에 성공·실패 기준을 확정하고, 구현 → 실패 경로 확인 → 정상 경로 확인 → PR → 배포/인수 증거를 남긴다. 실제 설정 변경·이슈 생성·push·PR·유료 호출에는 기존 승인 절차를 적용한다.
3. 검토자는 증거와 최신성을 확인하고 해당 영역을 재평가한다. **파일 존재·스킬 설치·모델 이름·도구 개수는 가점 증거가 아니다.**
4. 같은 결과를 여러 항목에서 참조할 수 있지만, 서로 다른 주장만 인정한다. 예를 들어 리허설의 요구사항별 인수 결정은 R2, 실제 모델 출력 품질은 T5의 증거다. 단순히 같은 성공 로그를 두 번 세지 않는다.
5. 만점은 **이 MVP 범위의 자체 평가 목표**다. 공식 해커톤 만점·보안 인증·무결함을 뜻하지 않는다. 기존 70점의 근거가 퇴행하면 재평가 점수는 낮아질 수 있다.

미확인·실행 실패·대상 0개·만료된 예외는 `완료`가 아니다. 적용할 수 없는 항목은 사유와 동등한 검증 방법을 먼저 합의한다. 불편하다는 이유로 제외하거나 다른 영역의 점수로 메우지 않는다.

### 요구사항·계획 — R1, R2

**담당:** 기능 이슈 assignee + 시연/인수 담당. **작업 대상:** [PROJECT.md](../CLAUDE.md#개요), [DEMO.md](../templates/submission/GUIDE.md), 관련 이슈.

| ID·개선 여지 | 실행 지침 | 만점 인정 증거 |
|---|---|---|
| R1 · 1점 | REQ-01~05 각각에 입력·정상/오류·범위 제외·담당·검증법을 연결하고, 이번 세부 평가 기준과 함께 팀의 채택 답변을 받는다. 변경 요구는 기존 기준을 몰래 완화하지 말고 변경 이유·영향을 기록한다. | 채택 일자·참여자·기준 버전, 요구사항→이슈→검증의 누락 없는 연결 |

**실패 판정:** 전체 흐름 5분 초과, 3주 요구 불충족, 근거 누락, 내보내기 불일치, 오류 후 진행 표시 잔류는 해당 기준 실패다. 예비안만 성공하면 live 성공으로 적지 않는다.

### 설계·계약 — D1, D2

**담당:** 계약 제공·사용 기능 담당 + 공용 변경 리뷰어. **작업 대상:** [architecture.md](../CLAUDE.md#구조), [contracts/](contracts/), backend schema/service, frontend 기능 `api.ts`.

| ID·개선 여지 | 실행 지침 | 만점 인정 증거 |
|---|---|---|
| D1 · 1점 | 알려진 radar/product→trends, frontend product→radar 의존을 목록화한다. 공유 타입·저장 인터페이스가 필요하면 최소 공용 경계를 별도 PR로 옮긴다. 유지해야 하는 예외는 계약·ADR에 이유·허용 방향·재검토 조건을 승인받고 새 역방향 의존을 검사한다. | 호출부 회귀 결과, 합의한 import 경계를 어기면 실패하는 검사, 담당자 답변. 전체 폴더 개편은 필수가 아님 |
| D2 · 1점 | 공개 DTO·SSE 이벤트를 기준 스키마/계약 fixture로 연결해 Pydantic·프론트 타입·mock을 자동 대조한다. 생성 타입이나 공통 fixture 중 기존 구조에 맞는 하나를 택하고, 오류 형태까지 포함한다. | 필수 필드 삭제·타입 변경·SSE 이벤트 불일치를 격리된 시험에서 검출한 결과와 복원 후 통과. 단순 `build` 성공이나 Markdown 동반 여부만으로 대체하지 않음 |

### 형상관리·리뷰 — V1, V2, V3

**담당:** 저장소 관리자 + 인프라 작업 담당. **작업 대상:** main 보호 설정, [PR 점수 설계](superpowers/specs/2026-10-03-pr-review-scoring-design.md), reviewer·handoff·PR 템플릿.

| ID·개선 여지 | 실행 지침 | 만점 인정 증거 |
|---|---|---|
| V1 · 1점 | 관리자가 현재 필수 체크 이름·우회 권한·리뷰 요청 처리·production 환경 접근 조건을 확인한다. 팀 정책과 다른 항목은 적용 또는 위험 결정을 남긴다. | 날짜 있는 설정 기록과 승인된 시험 PR의 실패 체크 머지 차단 확인. `main.protected=true`만으로 대체하지 않음 |
| V2 · 1점 | 기존 AI 블록 파서를 활용하도록 reviewer·handoff·템플릿을 연결한다. 최신 SHA·파일/줄 지적·조치·미확인을 기록하고, 변경 후 관련 리뷰를 갱신한다. | 최신/오래된/잘못된 블록 각각의 표시, 최신 변경에 대한 리뷰 답변. 블록은 자기 보고이며 AI 실행 사실을 인증하지 않음 |
| V3 · 1점 | 로컬 구현을 재작성하지 말고 자체 테스트와 실제 PR 워크플로를 확인한다. 설치 실패·아티팩트 누락·읽기 전용 토큰·코멘트 갱신 실패도 시험한다. | 테스트 명령 결과, 실행 URL·head SHA, 코멘트 1개 갱신·잡 요약·미측정 표시. 비차단 보고와 필수 CI 판정을 구분 |

**주의:** PR 점수는 자동 40 + AI 60의 다른 척도다. 오래된 리뷰는 현재 구현에서 경고만 하므로, 높은 점수가 최신 리뷰를 대신하지 않는다. 사람의 머지 원칙도 유지한다.

### 정적 품질 분석 — Q1, Q2

**담당:** 인프라 작업 담당 + 변경 기능 담당. **작업 대상:** `.github/workflows/`, `scripts/*.sh`, 기존 lint/type 설정.

| ID·개선 여지 | 실행 지침 | 만점 인정 증거 |
|---|---|---|
| Q1 · 1점 | 워크플로는 actionlint, 셸은 ShellCheck 등 한 가지씩 검토해 버전·검사 파일 목록을 고정한다. 기존 셸 dialect와 오탐을 먼저 분류하고 변경 PR에 연결한다. | 유효하지 않은 Actions 표현식·셸 인용 문제를 격리 사본에서 검출한 결과, 정상 파일 통과, 설치 실패를 별도 실패로 처리한 결과 |
| Q2 · 1점 | ruff/ESLint/ty의 경고·예외·검사 범위를 기준선으로 남긴다. `noqa`, `ty: ignore`, ESLint disable의 사유·담당·재검토일을 기록하고 새 예외는 리뷰한다. | 도구 버전·SHA별 진단 추이, 신규/해소/허용 항목 구분. 규칙 끄기·전역 제외로 좋아진 수치는 개선으로 인정하지 않음 |

**PEP 8은 이미 적용 중이다.** `E/W`·import 정렬·일부 naming·format을 CI가 검사한다. 코드·주석·독스트링 99자와 한국어 주석은 팀 선택이고, PEP 257의 `D` 규칙은 강제하지 않는다. `N`이 모든 이름의 의미나 상수 관례를 보장하지는 않으므로 이름·주석의 적절성은 리뷰한다. `B`는 bugbear이며 보안 전용 `S`가 아니다. 전체 PEP 8·보안 준수를 자동 인증한다고 표현하지 않는다.

| T5 · 2점 | T1 이후 현재 사용 모델·프롬프트·데이터·SHA를 고정하고 승인된 예산으로 Radar/Product eval과 UI 리허설을 수행한다. 출력 원본은 공개 가능한 내용만 보존한다. | 규칙 평가 1점, 실제 사용자 흐름·근거/사업 관련성의 사람 확인 1점. 모델·케이스 수·성공/실패·재시도·소요 시간·한계 명시 |

T2의 최소 시나리오는 다음과 같다. 테스트 도구를 추가하는 PR에서 명령·위치·CI 잡까지 정하고 이 문서에 연결한다.

| 묶음 | 필수 관찰 |
|---|---|
| 정상 | 국가/기간 변경 시 최신 차트, Radar 선택→Product 연결, 서버 근거·추론 구분, 정상 SSE 완료 |
| 내보내기·예비안 | 복사와 다운로드를 각각 실제 확인, 핵심 내용 일치, 스냅샷 연결·시각·모델 안내 |
| 실패·취소 | HTTP 429, SSE `error`, `done/error` 없는 종료, 사용자 중지, 재시도, 스피너 종료·늦은 이전 응답 무시 |

**호출 경계:** 저장된 Radar 기회를 골라도 Product UI는 먼저 실제 생성을 요청한다. 무호출 반복 연습은 Radar 스냅샷과 기존 Product Markdown/영상으로 한다. mock 성공을 새 LLM 생성 성공으로 쓰지 않는다.

### 보안·공급망 — S1~S5

**담당:** 관리자 + 인프라/기능 담당. **작업 대상:** 보안 설정, `.github/workflows/security.yml`, 의존성 선언/해결 결과, 기존 pytest·Vitest.

| ID·개선 여지 | 실행 지침 | 만점 인정 증거 |
|---|---|---|
| S1 · 1점 | gitleaks 체크·Dependabot alerts·Secret scanning·Push protection의 실제 활성화/지원 여부를 확인한다. 노출 대응·키 교체 담당도 정한다. | 비밀값 없는 설정·최신 실행·승인된 합성 테스트값의 차단 증거. 실제 키를 넣어 시험하지 않음 |
| S2 · 1점 | npm audit와 pip-audit 등으로 직접/전이 의존성을 검사한다. npm lockfile, Python의 실제 해결 환경·운영/개발 의존성을 구분한다. | CVE/GHSA·조회 시각·도구 버전·수정 버전·미검사 항목·종료 코드, 수정 후 재검사. 네트워크 실패/0대상은 clean 아님 |
| S3 · 1점 | CodeQL default setup을 우선 확인하고 Python·JS/TS를 실제 분석한다. 사용할 수 없으면 같은 위험 범위를 다루는 대안을 승인받는다. | 언어별 분석 범위·실행·분류/조치, 승인된 격리 예제로 검출 확인. ruff `S`만으로 다중 언어 SAST를 대체하지 않음 |
| S4 · 1점 | 입력 상한·CORS·한도·프롬프트 경계·출력 문자열의 부정 사례를 추가한다. CI의 PR 코드 실행/쓰기 토큰·시크릿 경계, 액션 pin을 검토한다. | 정상/거부 회귀 결과와 권한표·필요 권한 근거. AI 리뷰나 actionlint 통과를 보안 분석으로 중복 인정하지 않음 |
| S5 · 1점 | 배포와 같은 해결 버전 목록/해시를 보존하고 해당 의존성의 SBOM·라이선스 목록을 생성한다. 범위 의존성의 재현 전략을 결정한다. | SHA·배포 실행과 연결된 버전/출처/라이선스 산출물, 누락·사용 제한 검토. SBOM 존재만으로 CVE 0건을 주장하지 않음 |

차단 기준은 **팀 채택 대상 제안**이다. 신규 HIGH/CRITICAL을 우선 차단하고 기존 항목도 노출·악용 가능성으로 분류한다. 확인된 비밀값 노출·악용 가능한 치명적 결함은 점수와 관계없이 머지를 보류한다. 오탐/허용 위험에는 규칙·경로/패키지·근거·담당·만료·후속 이슈를 남긴다.

도구 설치·규칙 로딩·업로드 실패는 검사 실패로 남긴다. `|| true`, 일괄 제외, `npm audit fix --force`로 점수만 높이지 않는다. 외부 advisory 서비스로 전송되는 의존성 메타데이터와 보고서 공개 범위를 사전에 확인한다. 상세 선택 근거와 명령 한계는 [SDLC 9절](pipeline.md)을 따른다.

### 배포·복구 — L1, L2

**담당:** 배포 담당 + 서비스/DB 관리자. **작업 대상:** [deploy.md](pipeline.md#문제가-생기면), 배포 실행 기록, 격리 복구 환경.

| ID·개선 여지 | 실행 지침 | 만점 인정 증거 |
|---|---|---|
| L1 · 1점 | release마다 CI→`make ship` 머지 후 main 검사→`make serve` 스모크→변경 기능 인수를 연결한다. DB 변경이 있는데 마이그레이션이 적용되지 않았으면 인수를 보류하고 명시적으로 보고하도록 보완한다. | 같은 대상 SHA의 실행·health·기능 결과, migration 적용/미적용 로그와 실패 경로 확인. `db: ok`만으로 스키마 적용을 대체하지 않음 |
| L2 · 1점 | O2 목표를 먼저 합의하고 격리 환경에서 코드 revert와 DB 백업 복원을 각각 연습한다. 이전 앱·새 스키마 호환, 복원 데이터 검증, 부분 배포 실패 대응을 기록한다. | 시작/완료 시각·대상·명령·복구 SHA·데이터 대조·목표 충족 여부. 합의한 목표 미달은 개선 후 재시험 |

코드 revert는 DB 복원이 아니다. health는 **새 revert 배포 SHA**와 비교한다. `migrate.sh --dry-run`도 기록 테이블 생성·RLS 쓰기를 수행하므로 공유 DB에 사용하지 않는다. 공유 DB 직접 SQL·고의 장애·승인 없는 복원은 금지하며, 운영 적용은 마이그레이션 파일과 승인된 배포 절차로만 한다.

### 운영·회고 — O1~O4

**담당:** 운영/시연 담당 + 서비스 접근 권한자. **작업 대상:** [TEAM.md](../CLAUDE.md#충돌-방지-규칙-세-사람이-같은-것을-동시에-고치지-않게), 운영 설정, [worklog/](../templates/starter/README.md).

| ID·개선 여지 | 실행 지침 | 만점 인정 증거 |
|---|---|---|
| O1 · 2점 | 감시 대상·주기·타임아웃·연속 실패·복구 알림·수신/대체 담당을 정한다. health 지연·db 오류·배포 SHA 불일치를 구분하고 free 서비스 기동 지연을 고려한다. | 정기 관측 기록 1점, 격리/합성 장애의 실제 알림 수신·복구 알림·담당 확인 1점. 스케줄 파일만으로 인정하지 않음 |
| O2 · 1점 | 서비스별 RTO/RPO와 계산 시작/종료·데이터 범위·허용 손실·백업 보존을 합의한다. 무료 플랜에서 보장 못 하는 조건을 명시한다. | 승인된 목표와 L2 실측 비교, 목표 미달 조치. 근거 없이 숫자를 적거나 0손실을 약속하지 않음 |
| O3 · 1점 | GitHub·LLM 키·로컬 docker 환경의 주 담당/대체 담당 접근과 키 교체·비용 한도 확인 경로를 인수한다. | GitHub ID·권한 범위·확인일·인수 답변. 키/비밀번호 공유·원문 기록은 금지 |
| O4 · 1점 | 실제 장애 또는 승인된 리허설 1건을 발견→영향→원인/가설→조치→재확인으로 닫는다. 재발 방지 이슈의 담당·기한·완료 증거까지 연결한다. | 조치 후 동일 시나리오 재검증, 남은 위험·회고 답변. 후속 이슈를 만든 것만으로 종료하지 않음 |

개발 단계의 알림 현황·정책 선택·발송 인수 조건은 [파이프라인 알림 점검](PIPELINE-MODEL-SKILLS.md#8-단계별-notification-확인과-선택안)을 참고한다. PR 코멘트·CI 상태나 단계 완료 알림만으로 O1의 **정기 운영 감시·장애/복구 수신 증거**를 대체하지 않는다.

## 4. 실행 명령과 승인 경계

### 이미 있는 명령

저장소 루트 기준이다. 환경 구성은 저장소 셋업 문서를 따른다. 아래 코드는 **실행 예시이지 이번 작업의 통과 로그가 아니다.**

```bash
(cd backend && .venv/bin/ruff check . && .venv/bin/ruff format --check . && .venv/bin/ty check app tests evals && .venv/bin/pytest)
(cd frontend && npm run lint && npm test && npm run build)
(cd backend && .venv/bin/python -m evals.run_radar_eval --provider mock)
(cd backend && .venv/bin/python -m evals.run_product_eval --provider mock)
python3 scripts/test_pr_review_score.py
```

PR 채점 테스트는 현대 Python이 필요하므로 현재 워크플로 러너와 호환되는 인터프리터를 쓴다. 채점 스크립트 본체는 GitHub API/코멘트 쓰기를 수행하므로 로컬 테스트 대신 무심코 실행하지 않는다.

### 아직 없는 명령·장치

`npm run test:e2e`, coverage 잡, SCA/SAST 게이트, 정기 감시·복구 자동화는 이 문서로 생성되지 않는다. 도입 PR에서 **정확한 명령·버전·파일·실행 환경·실패 기준**을 확정하고 이 가이드에 링크한다. 없는 명령을 현재 가능한 절차처럼 복사하지 않는다.

| 작업 | 실행 전 확인 |
|---|---|
| 실제 LLM eval·UI 생성 | 사용자 승인, 공급자·모델·케이스 수 > 0, 호출/재시도 예산, 공개 데이터만 사용 |
| SCA/SAST·신규 테스트 도구 | 도입 승인, 의존성/CI 변경, 격리 환경, 라이선스·외부 전송 범위 |
| 관리자 설정·알림 연결 | 실제 권한 보유자, 변경 영향, 비밀값 없는 설정 기록 |
| 복구·재배포 | 대상 환경·데이터·중단/복원 계획, 사용자 승인. 사람 머지 원칙 유지 |

## 5. 이슈와 증거 양식

이슈 생성은 사용자 확인 후 수행한다. 아래 내용을 기존 기능/버그 템플릿의 해당 항목에 채운다. PR 본문도 저장소 템플릿을 유지한다.

```text
목표 / 연결 ID(R1 등) / REQ:
현재 부족한 점 / 포함·제외 범위:
담당자 / 영향받는 담당자 / 선행 항목 / 기한:
수정 파일·설정 / 필요한 승인·권한·비용:
성공 기준 / 실패·누락·권한 부족 시 판정:
검증 명령 / 격리 방법 / 배포·복구 영향:
```

완료 시에는 다음 증거를 이슈·PR·작업 기록에 남긴다. 원본 로그를 공개할 수 없으면 비밀값을 제거한 요약과 권한 있는 검토자의 확인을 남긴다.

```text
증거 ID / 연결 개선 항목 / 주장하는 완료 조건:
일시 / 수행자 / 검토자:
기준 SHA·미커밋 변경 여부 / 환경 / 도구·모델·규칙 버전:
명령 / 대상 수·범위 / 종료 코드:
정상 결과 / 실패 경로 결과 / 미실행·제외:
CI·PR·Deploy·보고서 링크:
예외 사유·담당·만료 / 남은 위험·후속 이슈:
판정: 완료 / 진행 / 차단 / 미확인
```

## 6. 100점 재평가 게이트

- [ ] 팀이 세부 평가 기준과 적용 범위를 채택했다.
- [ ] 25개 항목의 증거를 검토했고, 영역별 목표 합계가 100이며 중복 가점이 없다.
- [ ] 기존 70점 근거도 유지된다. 차단 결함·필수 검사 실패·기한 지난 예외가 없다.
- [ ] 코드·모델·규칙·설정이 바뀐 뒤 영향받는 결과를 갱신했다. 과거 성공을 현재 증거로 쓰지 않았다.
- [ ] 이슈→PR→CI→배포→인수와 복구·알림 실측을 연결했다.
- [ ] 검토자가 영역별 점수·근거·평가일·대상 SHA를 SDLC 평가표의 **새 평가 기록**으로 남겼다.

어느 항목이든 미확인이면 `목표 100 / 현재 확인된 점수와 보류 사유`로 보고한다. 문서·모델·스킬 추천만 반영한 현 단계는 **70점 기준선 유지, 개선 실행 대기**다.
