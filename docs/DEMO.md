> 배경·수용 기준은 [PROJECT.md](PROJECT.md#요구사항과-수용-기준), 예비안 구조는 [Radar 계약](contracts/radar.md)의 snapshot.

## LLM 비용 아끼기 (#66)
- **LLM을 쓰지 않는 반복 연습은 Radar의 "저장된 결과"와 미리 받은 Product Markdown·녹화 영상으로 한다.** Radar 스냅샷 조회는 LLM·한도를 쓰지 않는다.
- **저장된 기회를 선택해도 Product의 "프로덕트 설계"는 먼저 실제 생성을 요청한다.** 현재 UI의 Product "저장된 결과 보기"는 생성 실패 후에만 제공된다. 따라서 Radar → Product 전체 화면 흐름을 무호출 연습이라고 설명하지 않는다. Product 스냅샷 API 자체의 조회가 무료라는 것과 UI가 바로 그 결과를 보여준다는 것은 다르다.
- 실시간 생성(radar "기회 찾기", product "프로덕트 설계")은 **사용자 승인 후 전날 최종 점검 1회와 본 시연**에서만 한다.
- radar는 같은 요청(그룹사·국가·focus·개수)을 **6시간 동안 재사용**한다. 첫 생성이 끝난 뒤 다시 누르면 LLM 없이 바로 같은 결과가 나온다 (생성 중에 같은 요청을 또 보내면 둘 다 새로 생성한다).
  - 본 시연 6시간 안에 같은 조건으로 돌려 봤다면 시연에서도 저장된 결과가 바로 나온다. 실시간 생성을 보여주려면 그 안에는 같은 조건으로 돌리지 않는다.
  - 재사용 결과는 서버 메모리에 있어 재배포·Render 재시작이면 비워진다.
- 기본 일일 한도는 서버 전체 150건이다 (chat·radar·product 합산, `CHAT_DAILY_LIMIT`; 운영 설정이 우선). 새 Radar 생성은 재시도 없는 정상 경로에서 LLM 3회, 기본 호출 예산은 재시도 포함 최대 6회지만 앱 요청 한도는 1건이다. Radar 캐시 적중·스냅샷 API 조회는 LLM과 앱 한도를 쓰지 않지만, 그 전에 시도한 Product 생성은 별개다.

## 시연 순서 (목표 5분 이내)
| 순서 | 화면 | 할 일 | 예상 시간 | 말할 거리 |
|---|---|---|---|---|
| 1 | `/trends` | 대한민국, 기간 "전체" | 즉시 (LLM 없음) | 실무 가이드 23.2% → 34.1%, 기술 지원 17.4% → 4.1%, 사용량 순위 57위 → 25위. 개인 계정 기준이고 기업 계정은 빠져 있다 |
| 2 | `/radar` | **KT Cloud** 선택 → 기회 찾기 | 15~20초 | 기다리는 동안 단계(트렌드 → 사업 매칭 → 기회 발굴)를 설명한다. "재시도" 안내가 떠도 정상이다 |
| 3 | 기회 카드 | "데이터 근거"와 "AI 추론" 짚기 | - | 숫자는 서버가 실제 데이터로 채우고, LLM은 근거를 고르기만 한다 |
| 4 | `/product` | 추가 요구사항 "3주 안에 PoC" → 프로덕트 설계 | 약 50초 | 기능·아키텍처·PoC 계획 |
| 5 | Product Card | **복사** 또는 **.md** 받기 | - | 바로 기획서 초안으로 쓸 수 있다 |

표의 시간은 과거 관측을 바탕으로 한 예상치이지 SLA가 아니다. 리허설에서는 재시도 대기와 화면 전환을 포함해 실제 시간을 잰다.

## 리허설 통과 기준

| 확인 | 통과 기준 | 결과를 남기는 방법 |
|---|---|---|
| 전체 흐름 | `/trends` 진입부터 Product Markdown 저장까지 **5분 이내** | 시작·종료 시각, 총 소요 시간. 초과 시 어느 단계인지 기록 |
| REQ-01 트렌드 | KR·전체 기간의 지표와 출처·데이터 범위 설명 확인 | 화면과 API/계약 대조 |
| REQ-02 실시간 기회 | 요청 `count` 이하의 기회가 1개 이상, 각 근거 1개 이상, 추론과 구분 | 그룹사·국가·focus·count와 실제 기회 수, 새 생성/캐시 구분 |
| REQ-03 Product | 선택한 기회와 연결, 필수 설계 내용·PoC 계획 존재. "3주 안" 요청이면 **3주 이내** | 화면 기간을 직접 대조. 현재 eval의 4주 상한으로 대체하지 않음 |
| REQ-03 내보내기 | 복사와 `.md` 모두 사용 가능하며 핵심 내용이 화면과 일치 | 파일을 실제로 열어 제목·기능·PoC·근거 확인, 공개 가능한 보관 위치 |
| REQ-04 예비안 | 저장된 KT Cloud 기회 → 대응 Product까지 연결, 생성 시각·모델·예시 표시 | live와 별도 결과 행. 운영 한도를 일부러 소진하지 말고 안전한 환경에서 오류 경로 확인 |
| REQ-05 중지·오류 | 중지·연결 끊김·오류 후 스피너가 끝나며 적절한 안내 표시 | 로컬/mock에서 확인한 환경과 재현 절차. API mock 확인과 운영 확인을 구분 |

**판정은 구분해서 쓴다**: 전체 기준을 확인하면 `통과`, 예비안만 되거나 일부를 확인하지 못하면 `조건부(미확인 항목 명시)`, 핵심 흐름·근거·내보내기가 깨지면 `실패`다. 저장된 결과나 캐시 성공을 새로운 LLM 생성 성공으로 기록하지 않는다. 조건부·실패는 보완 후 재확인하거나 한계를 명시한 시연 결정을 받아야 한다.

PR 프리뷰는 백엔드 격리 환경이 아니다. 운영 API를 향하는 프리뷰에서 고의 장애·한도 소진·DB 쓰기로 실패를 재현하지 않는다.

## 문제가 생겼을 때
| 상황 | 대응 |
|---|---|
| radar 오류 (한도·장애) | 오류 카드의 **"저장된 결과 보기"** |
| product 오류, 기회가 저장된 결과에서 온 것 | 오류 카드의 **"저장된 결과 보기"** |
| product 오류, 기회가 실시간 생성된 것 | `/radar`로 돌아가 "기회 찾기" 옆 **"저장된 결과"** → 기회 선택 → 프로덕트 설계. 다시 실패하면 오류 카드의 "저장된 결과 보기" |
| "재시도" 안내가 계속됨 | 공급자 한도 또는 일시 오류일 수 있다. 안내와 로그를 확인하고, 1분이 넘으면 **중지** → "저장된 결과" |
| Render 응답 없음 | `/api/health`로 다시 깨운다. 안 되면 녹화 영상 |

저장된 결과를 보여줄 때 화면에 "{날짜}에 {모델}로 미리 만든 결과입니다. AI가 만든 예시이며 실제 사업 계획이 아닙니다"가 함께 나온다. 말할 때도 실시간 결과가 아니라고 밝힌다.
